# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Fleet is a multi-project Claude Code backlog orchestrator: a daemon polls GitHub repos for issues labeled `fleet:ready`, runs each one as a Claude Agent SDK worker session in its own git worktree, and ends every ticket at a PR for human review. A Vue dashboard (served by the daemon) shows the board and handles approvals/questions.

## Commands

```bash
pnpm install
pnpm typecheck                  # turbo run typecheck: tsc per package (vue-tsc for dashboard), cached
pnpm test                       # turbo run test: vitest per package, cached
pnpm build                      # turbo run build (currently just the dashboard)
pnpm daemon -- --dry-run --once # poll and report; changes nothing
pnpm daemon -- --once           # one full cycle, then exit (no dashboard server: worker approvals are auto-denied immediately)
pnpm mcp                        # run the stdio MCP server directly (normally launched by a repo's .mcp.json); needs FLEET_REPO or FLEET_PROJECT+config, never a running daemon
pnpm daemon                     # real loop + dashboard on :4400
pnpm daemon:supervised          # daemon under scripts/fleet-supervisor.mjs: auto-relaunches on crash or restart request
pnpm daemon init-labels         # create fleet:* labels in each configured repo
pnpm daemon sync-templates      # stamp the fleet-backlog skill + MCP registration into each configured repo for each agent in its `agents` (claude: .claude/skills + .mcp.json; codex: .agents/skills + .codex/config.toml), and regenerate/prune its .github/ISSUE_TEMPLATE fleet issue forms from fleet.yaml
pnpm fleet:init -- --path <repo> [--repo owner/name] [--agents claude,codex] [--dashboard-port <n>]   # same stamping for one repo, writing its gitignored fleet.config.json; no daemon involved. Relative paths resolve against INIT_CWD (where pnpm ran), never packages/mcp
pnpm dashboard:dev              # Vite on :4401, proxying /api and /ws to :4400
pnpm dashboard:build            # turbo-cached dashboard build (every `pnpm daemon` run does this first)
```

Task running is turborepo (`turbo.json`): `build`, `typecheck`, and `test` are all per-package cached tasks (`dist/**` for `build`, logs-only for the other two), and `@fleet/daemon#start` declares `@fleet/dashboard#build` as a dependency, so `pnpm daemon` always installs and rebuilds the dashboard before the daemon boots — the daemon serves `packages/dashboard/dist` off disk, so a stale build there silently ships old UI. Arguments still pass through (`pnpm daemon -- --once`, `pnpm daemon init-labels`); the daemon filters the `--` that turbo forwards verbatim.

`typecheck` and `test` each `dependsOn` their own task name prefixed `^` (e.g. `"typecheck": { "dependsOn": ["^typecheck"] }`), so a package's cache key folds in the task hash of every internal workspace dependency it declares in `package.json` — daemon, mcp and dashboard all depend on `@fleet/shared`, and daemon and mcp on `@fleet/github`, so each invalidates whenever those change. This only works because every package in the chain (including `@fleet/shared` itself) declares matching `typecheck`/`test` scripts in its own `package.json`, each scoped to just that package (`tsc -p tsconfig.json`; `vitest run --root ../.. packages/<name>` against the shared root `vitest.config.ts`) — a package with no such script breaks the chain silently rather than erroring.

Verification is `pnpm typecheck` plus `pnpm test`, plus a `--dry-run --once` daemon run for anything that isn't unit-tested. The daemon shells out to `gh` for all GitHub access, so `gh auth login` must have been run. Runtime config is `fleet.config.json` (gitignored — when changing the config shape, update both `fleet.config.example.json` and the schema in `packages/shared/src/config.ts`). This repo's own `fleet.yaml` warms turbo's build/typecheck/test caches after `pnpm install` at claim time (`allowFailure: true` per step, since a red baseline on `main` must not block worktree creation — see `BuildSpecStep.allowFailure` in `packages/shared/src/buildspec.ts`).

## Architecture

pnpm workspace, five packages, no build step for backend code:

- **`packages/shared`** — holds everything both sides need, split by concern behind an `src/index.ts` re-export barrel — among them `labels.ts` (label constants + label helpers), `config.ts` (zod config schemas), `contracts.ts` (`WorkerResultSchema`/`PlanResultSchema`/`MachineReviewResultSchema`/`PlanReviewResultSchema` structured-output contracts), `tickets.ts` (`TicketRecord`/`FleetState`/approval types), `board.ts` (`BoardTicket`/`ClosedTicketRecord`/history/journal types), `buildspec.ts` (the `fleet.yaml` `BuildSpec`/profile/tier schema + selectors), `intake.ts` (issue-body intake lint), `ticket-intake.ts` (the one ticket-filing contract: `CreateTicketSchema`/`labelsForNewTicket`/`bodyWithDependsOn`/`parseDependsOn`, run by both the REST route and the MCP), and `log.ts`. `config.ts` also carries `ProjectsOnlyConfigSchema`, the lenient projects-only view of `fleet.config.json` for consumers that never run a daemon. Nothing in shared may import `node:fs`/`node:child_process`: the dashboard bundles it. Consumed directly as TypeScript source (root tsconfig `paths` + `allowImportingTsExtensions`; imports use explicit `.ts` extensions) — always via `@fleet/shared`, never by importing a concern module directly.
- **`packages/daemon`** — Node daemon run via `tsx` (never compiled). Hono REST + WebSocket server, Claude Agent SDK sessions.
- **`packages/github`** — `@fleet/github`: "talk to GitHub through `gh`". `exec.ts` (`run`/`runJson`/`runJsonPaginated`/`runShell`), `issues.ts` (`createIssue`/`getIssue`/`listFleetIssues`/`listIssueStates`, taking a narrow `RepoRef = { githubRepo }` that `ProjectConfig` satisfies structurally), and `labels.ts` (`ensureFleetLabels`/`ensureTypeLabel`). Depended on by daemon and mcp, never the dashboard. The daemon's `github/github.ts` re-exports these so its call sites and test mocks keep one import path; `github/exec.ts` there is a re-export shim for the same reason.
- **`packages/mcp`** — stdio MCP server (`@modelcontextprotocol/sdk`). The rule: **backlog reads go to GitHub, derived-state reads go to the daemon, and filing goes through the daemon when one is configured (else GitHub).** `tickets.ts` (`GithubTickets`) files and lists via `@fleet/github`, running the shared ticket-intake contract first; `DaemonFirstTickets` wraps it to file via the daemon's REST route (so the daemon's `gh` identity opens the issue — the contributor floor and label permissions depend on it), falling back to `GithubTickets` only when the daemon is unreachable; `daemon.ts` is the REST client for board/history/report/journal. `resolve.ts` is the only env reader (`FLEET_REPO` → else `FLEET_PROJECT` looked up in a `fleet.config.json` found by `config-file.ts`'s upward search or `FLEET_CONFIG`; daemon URL from `FLEET_URL`, else the config's `dashboardPort` (a full daemon config — one with `worktreeRoot` — implies 4400), else none — no probing, no fallback). One file per tool under `tools/`, each declaring `home: "tickets" | "daemon"`; `registerTools` skips daemon tools when no daemon resolved, so the agent never sees a tool it cannot use. `stamp/` holds the per-agent stampers (`claude.ts`: `.claude/skills` + a JSON merge into `.mcp.json`; `codex.ts`: `.agents/skills` + a line-level merge of the `[mcp_servers.fleet]` table into `.codex/config.toml` that preserves everything else verbatim, including line endings, and refuses dotted-key/inline fleet definitions it can't cut safely). **Committed stamped files never name a path**: `buildFleetEntry` (`stamp/entry.ts`) is just `node .fleet-mcp/launch.mjs` + `FLEET_PROJECT`, `stampProject` also writes the machine-neutral launcher (`templates/fleet-mcp/launch.mjs`), and this machine's `fleetDir`/`dashboardPort` go only into the repo's gitignored `fleet.config.json` (`stamp/repo-config.ts`, which also adds it to the repo's `.gitignore` and skips the fleet checkout itself). The launcher finds that config upward (or via `FLEET_CONFIG`, which `index.ts` exports so worker sessions in worktrees — which lack gitignored files — still resolve it) and runs `node --import tsx` on the MCP entry directly, so no shell or `.cmd` shim is involved on Windows. The daemon's `sync-templates` imports the stampers via `@fleet/mcp/stamp`, and `init.ts` (`pnpm fleet:init`) runs them for one repo. `templates/*.example` show the resulting files, with placeholder paths only.
- **`packages/dashboard`** — Vue 3 + Tailwind 4 + Vite SPA. Polls `/api/board` and listens on `/ws` for `board-updated` / `approvals-updated` pings (the WS carries no payloads; clients refetch).

### Daemon flow (the part that spans files)

`packages/daemon/src` is grouped by concern: `loop/` (the poll loop and everything it coordinates), `session/` (worker sessions, machine review, approvals), `github/` (GitHub/git shelling out), `server/` (the dashboard's REST/WS API), `store/` (on-disk state/history/journal), and root files for cross-cutting pieces (`index.ts`, `config.ts`, `events.ts`, `log.ts`, `notify.ts`, `sync-templates.ts`, `throttle.ts`, among others). Tests are colocated with their subject module (e.g. `loop/loop.claim.test.ts` next to `loop/claim.ts`).

`index.ts` wires everything and owns the poll loop. Each cycle, `FleetLoop` (`loop/loop.ts`) lists `fleet:*` issues per project via `github/github.ts`, claims ready ones up to `maxConcurrent`, and for each: swaps labels, creates a worktree + `fleet/<issue>` branch (`github/worktree.ts`), records a `TicketRecord` (`store/state.ts`), and runs a `WorkerSession` (`session/worker.ts`).

`FleetLoop` itself is only a coordinator: it owns the shared mutable state (the in-flight/live-session/reply-waiter maps, the board cache, the stores) and hands it to every other module as a `LoopContext` (`loop/context.ts`, which also holds the `key`/`countRunning`/`track`/`markWorking` helpers they all share). The concerns each live in their own file in `loop/` as plain functions taking that context first — the ones this narrative leans on include `claim.ts` (per-project cycle + claiming), `runner.ts` (opening/resuming a session, model selection, `canUseTool`), `supervise.ts` (the turn state machine + review gates), `finish.ts` (the completed/planned/blocked/failed terminal paths), `pause.ts` (plan usage-limit pause), `recovery.ts` (stall flagging + auto-resume), `reviews.ts` (PR-feedback resumption), `board.ts` (board projection + finished-ticket cleanup), `operator.ts` (dashboard reply/restart), and `shutdown.ts` (stop-now's session abort); more single-concern modules in the same shape sit alongside them (`.claude/skills/add-daemon-feature` keeps the exhaustive map). Anything a module needs from another it imports directly; nothing calls back into `FleetLoop`.

`WorkerSession` (`session/worker.ts`) wraps one Agent SDK `query()` with a streaming input queue so the supervisor can inject follow-up messages into a live session. Workers run with `permissionMode: "acceptEdits"`, `settingSources: ["project"]` (so the *target repo's* `.claude/` skills, agents, and CLAUDE.md load inside worker sessions), and a JSON-schema `outputFormat` — every code turn must end in a `WorkerResult` (`completed` | `blocked`). A `fleet:plan` issue runs the same machinery as `kind: "plan"` instead: its `outputFormat` is `PlanResult` (a list of child ticket titles/bodies/priority/tier) and a `PreToolUse` hook denies `git commit` on top of the push/PR/label restriction below, since a planner must stay read-only. Independent of `kind`, that same hook (`denyForbiddenBash`/`denyForbiddenPlanBash` in `session/worker.ts`) mechanically denies `git push`, `gh pr` (except read-only `view`/`diff`), `gh issue edit|close|comment`, and `gh label` over plain Bash — allowlisted tools bypass `canUseTool`, so the "orchestrator owns pushing/PRs/labels" half of the worker contract has no other enforcement point.

The supervision loop in `supervise()` (`loop/supervise.ts`) is the core state machine: `completed` → machine review gate → verify commits exist, push, open PR (`fleet:review`). The machine review (`session/review.ts`, on by default, opt out per-project with `machineReview: false`) runs a one-shot read-only session on `lightModel ?? model` over the local branch diff *before* anything is pushed; findings steer the still-live worker session through exactly one fix round (`TicketRecord.machineReviewOutcome` is the once-per-ticket cap), and any reviewer failure fails open to human review. A completed **plan** goes through its own `planReviewGate` (`supervise.ts`) instead — the same one-shot read-only reviewer shape over the proposed `tickets[]` (via `PlanReviewResultSchema`), sharing the `machineReview` opt-out, the `machineReviewOutcome` once-per-ticket fix-round cap, and the fail-open contract — and only then `finishPlanned` files each proposed ticket as a child issue (tagged with its suggested tier label, and `fleet:ready` immediately if `planChildrenReady`, else `fleet:backlog` — a board-visible, not-yet-claimable state) and puts the epic into `fleet:review` without a PR. The dashboard's **Accept plan** (`acceptPlan` in `loop/operator.ts`, via `POST /api/tickets/:project/:issue/accept-plan`) releases the epic's still-open backlog children to `fleet:ready` and closes the epic; `closeFinishedEpics` (`loop/epics.ts`) is the fallback that closes a never-accepted epic once all its children close. A single backlog ticket is released with `POST /api/tickets/:project/:issue/ready`. `blocked` (either kind) → post the question to the issue's status comment (`fleet:needs-input`), then hold the session open for `replyWaitMinutes` awaiting a dashboard reply — a reply steers the live session; after timeout the session closes but stays resumable via `resume: sessionId`. `reply()` (`loop/operator.ts`) handles all three cases (waiting session, live session, cold resume). A run that errors outright (not `blocked`) auto-retries once on `elevatedModel` when `shouldAutoElevate` allows it (project opts in via `autoElevateOnFailure`, default on, and this ticket hasn't already been elevated), before falling back to `fleet:needs-input`.

Outside the claim loop, each cycle also: resumes stalled tickets (`pickAutoResumable` — no activity for `stalledAfterMinutes`, or orphaned by a restart — resumed once each from their last session) and resumes tickets in `fleet:review` that picked up changes-requested reviews or fresh inline comments (`pickReviewCandidates`/`addressReviews`, opt out per-project with `autoAddressReviews: false`; a `lastReviewHandledAt` watermark stops the same feedback firing twice). A session hitting the account's plan usage limit pauses claims/resumes across every project (`FleetState.pausedUntil`) until the parsed reset time (plus `limitResumeSlackMinutes`, or `limitDefaultBackoffMinutes` if no reset time parsed) — the triggering ticket is left `stalled` so the auto-resume above picks it back up once the pause lifts.

Tool calls outside the allowlist and `AskUserQuestion` route through `canUseTool` → `ApprovalManager` (`session/approvals.ts`), which parks the promise until the dashboard answers via `POST /api/approvals/:id` or the timeout denies it. Denial messages are crafted to push the worker toward finishing as `blocked` rather than dying. In `--once` mode there's no dashboard to answer with, so `makeCanUseTool` (`loop/runner.ts`) skips `ApprovalManager` entirely and denies immediately instead of waiting out `approvalTimeoutMinutes`. `ticketTimeoutMinutes` bounds a turn's own wall-clock work, not a human's response time: `makeCanUseTool` pauses the session's `TurnClock` (`session/turn-clock.ts`) for the duration of every parked approval and resumes it (with whatever budget was left, not a fresh allotment) once the approval settles, so an `approvalTimeoutMinutes` measured in hours doesn't require a matching `ticketTimeoutMinutes`. That exclusion is capped per turn by `approvalPauseCapMinutes` (passed to `TurnClock.start` as `maxPausedMs`): past it the countdown runs again even under a parked approval, so a worker requesting approval after approval can't hold its `maxConcurrent` slot indefinitely. A ticket whose approval has been pending longer than `approvalYieldMinutes` is *yielded*: `countActive` (`loop/context.ts`) leaves it out of every capacity decision (claiming, stall auto-resume, review and comment cold-resumes) so the project can take the next ticket while it keeps waiting; drain, the board's running count and the duplicate-track guard still use `countRunning`. When a yielded approval is answered the project can briefly run over `maxConcurrent` — claims just hold (logged once) until it drops back. Discord posts are serialized per webhook URL (`postSerially` in `notify.ts`) because the event bus fires listeners without awaiting them. `flagStalled` (`loop/recovery.ts`) likewise skips a ticket with a pending approval, since a parked approval produces no SDK activity by design.

Stopping the long-running daemon (`--once` never reaches this code) goes through `FleetLoop.beginShutdown()` — a synchronous once-only guard shared by `POST /api/daemon/shutdown` and the `SIGINT`/`SIGTERM` handlers in `index.ts` — followed by one of two modes. `shutdownDrain()` enables the same pause `setPaused` does, then resolves once `running` is empty: every live ticket reaches completed/blocked/failed on its own, so there's no label or status-comment churn to guard against. `shutdownNow()` (`loop/shutdown.ts`, wired to Ctrl+C/SIGTERM) aborts every `WorkerSession.abortController` in `live` immediately — releasing any parked `replyWaiters` too, so a blocked session doesn't ride out `replyWaitMinutes`. The abort surfaces to `supervise` as an ordinary errored turn, so `finishFailed` needs to know not to report it: a `ctx.stopping` scope set (parallel to the `restarting` one `restartTicket` uses) steers that turn to `stalled` instead of `fleet:needs-input`, leaving `sessionId` intact (already written back by `runSession`'s `finally`) and clearing `autoResumed` — so the next boot's `recoverStalled` resumes it for free instead of burning its once-only budget recovering from an unclean stop, which is the whole point of this over just killing the process.

`beginShutdown()` flips an in-memory `isShuttingDown()` flag on `LoopContext`, checked (not just `cycle()`'s `paused`, which is snapshotted once per cycle and goes stale across the several `await`s inside `cycleProject`) immediately before every place new work gets `track()`ed — the claim loop in `loop/claim.ts`, the auto-resume loop in `loop/recovery.ts`, `addressReviews` in `loop/reviews.ts`, and the cold-resume branch of `reply()` in `loop/operator.ts` — so a `cycle()` already mid-flight when shutdown begins can't claim or resume past that point. Because that still can't cancel a claim/resume that's already past its own check, `stopLiveSessions` doesn't sweep `live` once: it re-scans every 200ms for the whole drain window, aborting anything newly there, so a straggler still ends up gracefully `stalled` instead of getting killed uncleanly by the `process.exit(0)` that follows.

### Integration boundary

Cross-cutting integrations (Discord notifications, the dashboard's WS broadcast, and any future one — a bot with approve/deny buttons, say) never get wired directly into the ticket lifecycle. Instead `loop/context.ts`'s `LoopContext` carries `events: FleetEvents` (`events.ts`), a thin typed wrapper over `node:events` (`FleetEventMap`: `ticket:needs-input` / `ticket:pr-opened` / `ticket:failed` / `ticket:auto-merged` / `ticket:stale-released` / `daemon:paused` / `approval:requested` / `approval:settled` / `board:updated` / `digest:ready`). The loop emits (`ctx.events.emit(...)` at each terminal path in `finish.ts`/`pause.ts`/`claim.ts`/`automerge.ts`/`heartbeat.ts`/`digest.ts`; `ApprovalManager`, `session/approvals.ts`, emits its own two off the same bus) and knows nothing about who's listening — `loop/` never imports `notify.ts`. Each integration subscribes independently: `notify.ts`'s `subscribeDiscordWebhook` turns ticket/pause/digest events into the existing Discord webhook calls, and `server.ts` turns `board:updated`/`approval:*` into the WS `board-updated`/`approvals-updated` pings. `FleetEvents.emit` isolates the emitter from every subscriber — a throwing or rejecting listener is logged and swallowed, never propagated, so a broken integration can't affect the ticket path that emitted. The only path back the other way is the existing operator API (`ApprovalManager.resolve`, `reply()`, `restartTicket`) — an integration reacts to what it's told, it never reaches back into `loop/` directly.

### State model — key invariant

GitHub labels are the source of truth for ticket status; `.fleet/fleet.db` — a SQLite database opened via `node:sqlite`, with `StateStore`/`HistoryStore` (`store/state.ts`) as thin wrappers over the schema/CRUD/migration helpers in `store/db.ts` — is operational cache only. It holds per-ticket records (worktree paths, session IDs, cost, model usage, and the `lastReviewHandledAt`/`autoElevated`/`isPlan` fields the behavior above depends on) in a `tickets` table, plus daemon-wide fields in a `daemon_state` key/value table — `pausedUntil` for the plan usage-limit pause, `paused` for operator drain mode (both gate claims/resumes via `isPaused` in `loop/pause.ts`), and `pausedProjects` for per-project pauses (`setProjectPaused`/`isProjectPaused` in `store/state.ts`) — and a `spend_ledger` table backing the rolling spend window. Per-ticket session journals (`Journal`/`readJournalTail`, `store/journal.ts`) live in a `journal_entries` table, indexed on project+issue and on `ts`; `summarize()` (`session/worker.ts`) turns each SDK message into one entry, including assistant `thinking` blocks and plain-text `"user"`-message content (operator/dashboard steering, echoed back through the message stream by `session.send()`) — both previously dropped. `journal_entries` has no retention policy yet (unlike `daemon_events`'s 30-day age-out) since nothing has read it back in production long enough to say what's safe to drop; trimming later is a one-line indexed `DELETE`. On boot, `StateStore.clearLiveFlags()` reconciles orphaned `running` tickets to `stalled` since no sessions survive a restart. Cleanup (worktree + branch removal) only happens once the PR is merged/closed *and* the issue is closed, at which point the ticket's record moves from `tickets` into the `history` table (`HistoryStore`, unbounded — nothing is ever trimmed) so the dashboard's Done column can still show it. The first boot against a pre-existing `.fleet/state.json`/`history.json` imports both into `fleet.db` and renames them to `*.imported.bak` (never deleted); later boots are a no-op since `fleet.db` already exists. Journals predate `fleet.db` (#130 deliberately left them as JSONL), so their own one-time import from `.fleet/journals/<project>/<issue>.jsonl` can't piggyback on that "only when the db is new" gate — `migrateJournalsFromJsonl` runs on every boot instead, and is one-time in effect because imported files are renamed to `*.imported.bak`, leaving nothing to import on the next scan.

Model selection is layered (most specific wins): skill/agent `model:` frontmatter in the target repo → `fleet:elevate` label (uses project `elevatedModel`) or `fleet:light` label (uses project `lightModel`) → the matched `fleet.yaml` type's declared `tier:` (`selectModel`/`resolveTypeTier` in `loop/runner.ts`; re-read fresh on every session open, same as `contract:`/`review:`) → per-project `model` config → CLI default. Plan decompositions can suggest a tier per child ticket, which becomes one of these labels on the filed issue.

## Conventions

- ESM everywhere, Node built-ins imported as `node:*`, relative imports carry `.ts` extensions.
- All GitHub mutations go through `github/github.ts` helpers in the daemon, or `@fleet/github` directly in the mcp package (both shell out to `gh` via `run()` from `@fleet/github`); don't call `gh` directly elsewhere.
- Status is reported to GitHub as a single continuously-updated status comment per issue (`upsertStatusComment`), not a stream of new comments.
- This daemon is developed and run on Windows; config paths use forward slashes (see `fleet.config.example.json`).
